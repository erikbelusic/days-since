# days-since

> **DAYS WITHOUT AN INCIDENT: 0**

**days-since** is a small Ruby on Rails app that shows how many days each online service has gone without an incident. It reads the public status pages of services you depend on (GitHub, Cloudflare, Stripe, …) and turns each one into a counter card, like the *"DAYS WITHOUT AN INCIDENT"* board on a construction site.

It is **local-first**: run it on your own machine without logging in. It is also **cloud-ready**: every subscription belongs to a `User` from day one, so the same code can later run as a hosted, multi-user app.

---

## Features (MVP)

- **Day counters** for each service, computed in your own time zone.
- **Two feed providers**
  - **Atlassian Statuspage** JSON API (`<status-url>/api/v2/incidents.json`). Used by GitHub, Cloudflare, Atlassian and many others.
  - **Generic RSS/Atom** fallback for any other status page tool.
- **Auto-detection**: paste a status page URL and the provider is detected for you. You can override the result.
- **Shared polling**: users who subscribe to the same status URL share one `Feed` record and one polling schedule.
- **Live updates**: cards refresh through Turbo Streams when new incidents arrive.
- **Per-user themes**: a clean default theme with light/dark mode, plus a **"Worksite Safety Sign"** parody theme with hazard stripes, industrial type and a site-board counter.

## Getting started

### Prerequisites

- Ruby **4.0.9**. The version is pinned in `.ruby-version`, and the maintainer uses [mise](https://mise.jdx.dev/).
- SQLite 3
- Google Chrome or Chromium, used by Cuprite for system specs

### Setup

```sh
git clone git@github.com:erikbelusic/days-since.git
cd days-since
bin/setup --skip-server          # installs gems, prepares the databases
bin/rails db:seed                # optional: GitHub, Cloudflare and Slack for the local user
SINGLE_USER_MODE=true bin/dev    # web server + Solid Queue poller + Tailwind watcher
```

Then open <http://localhost:3000>. New status pages are polled right away, then every 5 minutes.

To try multi-user mode, create an account (there is no public sign-up) and run without the flag:

```sh
bin/rails users:create EMAIL=you@example.com   # prints a generated password
bin/dev
```

### Running tests and checks

```sh
bundle exec rspec      # full test suite
bin/rubocop            # lint (rubocop-rails-omakase)
bin/brakeman           # static security scan
```

## `SINGLE_USER_MODE`

The app always has a `User` model, and every subscription belongs to a user. `SINGLE_USER_MODE` only changes **how the current user is resolved**.

| `SINGLE_USER_MODE` | Behavior |
|---|---|
| unset or `false` | Multi-user mode. Users log in with email and password through the Rails 8 authentication generator. There is **no public sign-up**: an admin creates accounts (by invite). |
| `true` | No login. On the first request, `current_user` resolves to a default local user, created with `User.find_or_create_by!(email_address: "local@days-since.local")` and a random password. Login and session routes redirect to the dashboard. |

`SINGLE_USER_MODE` is supported in **every environment, including `production`**. That lets you run a production build on your own machine or home server. In production the app logs a **warning at boot** as a reminder that authentication is off, so never enable it on a server reachable from the public internet.

Because all data hangs off a real `User` row, switching from single-user to multi-user mode later only means giving the local user a real email and password.

## Architecture overview

### Data model

```
User ──< Subscription >── Feed ──< Incident
```

| Model | Key columns | Notes |
|---|---|---|
| `User` | `email_address`, `password_digest`, `theme`, `time_zone`, `default_min_severity`, `no_incident_display` | Auth columns come from the generator. `theme` is validated against the code registry. `default_min_severity` defaults to `minor`. `no_incident_display` is `infinity` (default) or `since_tracking`. |
| `Session` | (generator) | Rails 8 auth sessions. |
| `Subscription` | `user_id`, `feed_id` (unique pair), `display_name`, `min_severity`, `position` | `min_severity` is an optional override; blank means use the user's default. `position` sets the dashboard order. |
| `Feed` | `url` (canonical, unique), `provider` (`statuspage` \| `rss`), `name`, `site_url`, `last_polled_at`, `last_success_at`, `next_poll_at`, `last_error`, `consecutive_failures`, `etag`, `last_modified` | One row per canonical status URL, shared by all subscribers. |
| `Incident` | `feed_id`, `external_id` (unique per feed), `title`, `impact`, `status`, `url`, `started_at`, `resolved_at` | Every incident is kept, so streak history and stats are possible later. |

**Feed deduplication.** Submitted URLs are normalized (lowercase host, no trailing slash or query string) and resolved to their **canonical API/feed URL** before lookup. So `githubstatus.com` and `githubstatus.com/api/v2/incidents.json` map to the same `Feed`.

**Orphaned feeds.** When the last subscriber leaves, the `Feed` and its incident history are **kept but no longer polled**. Polling starts again if someone subscribes again.

### Counter semantics

For a given subscription:

1. **Relevant incidents** are those whose `impact` is at or above the effective minimum severity: `subscription.min_severity` if set, otherwise `user.default_min_severity`. Statuspage impacts rank `none < minor < major < critical`. RSS entries have no severity, so they always count.
2. **Scheduled maintenance** never resets the counter.
3. If a relevant incident is **unresolved**, the card shows **`0` with an `ONGOING` state**.
4. Otherwise, the count is the number of **calendar days in the user's time zone** from the last relevant incident's `resolved_at` until today.
5. If there are **no relevant incidents on record**, the card shows either **`∞ No incidents on record`** (default) or the number of days since we started tracking the feed. The user's `no_incident_display` setting picks which.

### Providers and auto-detection

Detection runs **synchronously when the subscription form is submitted**, so errors show up right away:

1. Load the URL, following redirects (for example `githubstatus.com` redirects to `www.githubstatus.com`).
2. Probe `<root>/api/v2/summary.json`. If it responds, the provider is **Statuspage**, polled at `<root>/api/v2/incidents.json`. Statuspage wins even when the page also advertises a feed.
3. Otherwise, if the URL is itself an RSS/Atom feed, the provider is **RSS**.
4. Otherwise, look for an RSS/Atom `<link rel="alternate">` in the page.
5. Otherwise, try a few common feed paths (`/feed`, `/feed/rss`, `/history.atom`, …). Slack and Heroku publish feeds without advertising them.
6. If none of these work, show a validation error.

The user can **manually override** the detected provider.

**RSS/Atom incident model:** each entry is treated as an incident that starts *and* resolves at its publish time. RSS has no structured resolved state.

HTTP goes through **Faraday**, and RSS/Atom is parsed with **Feedjira**.

### Polling

- A **Solid Queue recurring job runs every 5 minutes**. It enqueues one poll job for each `Feed` that has at least one subscriber and whose `next_poll_at` has passed.
- Requests are **conditional GETs** (`ETag` / `If-Modified-Since`), so a feed that hasn't changed costs almost nothing.
- Failures use **exponential backoff**, capped at about 1 hour. The backoff is tracked in `consecutive_failures` and `next_poll_at`.
- New or changed incidents trigger **Turbo Stream broadcasts**, so open dashboards update live.
- In development, Solid Queue runs inside Puma through `bin/dev` (the Rails 8 default).

### Theming

Themes are defined in code and added by pull request. There is no theme table in the database.

- **Registry:** `Theme.all` lists the available themes, and `User#theme` is validated against it.
- **Color and typography:** each theme defines CSS custom properties in `app/assets/tailwind/themes/<theme>.css`, scoped by `<html data-theme="<theme>">`. Tailwind utilities such as `bg-surface` and `text-accent` map to those properties.
- **Structure and graphics:** themes can provide their own partials, for example `app/views/themes/<theme>/_feed_card.html.erb`. A theme that doesn't provide a partial falls back to the `default` theme's version.
- **Scope:** a theme controls the whole page: header, background, fonts and cards.
- **Fonts:** fonts are self-hosted under OFL licensing (for example an industrial face such as Oswald or Bebas Neue for Worksite). The app never loads fonts from a third-party CDN.
- **Dark mode:** the default theme supports light and dark through `prefers-color-scheme`.

See [`CLAUDE.md`](CLAUDE.md) for the step-by-step guide to adding a theme.
